# SyllabusSite

A single-page website presenting a course syllabus. Students should be able to open it and find the schedule, policies, and contact info quickly, on any device, and print it cleanly.

## Stack

- Plain HTML, CSS, and JavaScript. No framework, no bundler, no build step, no npm dependencies unless the user asks for one.
- The site must work by opening `index.html` directly in a browser (`file://`) and when hosted as static files.
- Use relative paths for all assets. No absolute (`/css/...`) paths.

## File layout

```
index.html          # the entire page; all content lives here
css/styles.css      # all styles
js/main.js          # small enhancements only (nav highlighting, smooth scroll)
assets/             # images, downloadable PDFs (e.g. the printable syllabus)
```

Keep this structure unless there is a good reason to change it. If a file isn't needed yet, don't create it.

## Content

The syllabus content is the product. Treat it as the source of truth and never invent details.

- Do not fabricate dates, grading weights, instructor names, emails, office hours, room numbers, or policies. If information is missing, use an obvious placeholder like `[TBD]` and tell the user.
- Keep content in semantic HTML, not generated by JavaScript, so it is readable without JS and indexable.
- Typical sections, in order: course header (title, term, meeting time/place; no course code), instructor and contact, course description, learning objectives, materials, grading breakdown, weekly schedule, policies (attendance, late work, academic integrity), accessibility and support resources.
- The weekly schedule is a real `<table>` (week, dates, topic, readings, assignments due) with `<th scope>` headers, not a grid of divs.
- Grading weights must sum to 100%. Check this whenever they change.

## Page structure

- One `<h1>` (the course title), then `<h2>` per section, `<h3>` below that. Don't skip levels.
- Each section is a `<section id="...">` with a short kebab-case id (`#schedule`, `#grading`). The sticky nav links to these ids.
- Use landmarks: `<header>`, `<nav>`, `<main>`, `<footer>`.

## Style and design

- Mobile-first CSS. Layouts must work from 320px wide up; no horizontal page scroll.
- Define colors, spacing, and fonts as CSS custom properties on `:root`. Do not hardcode colors elsewhere.
- Support dark mode with `prefers-color-scheme`.
- Use system font stacks by default. Don't add web fonts or CDN links without asking.
- Wide tables scroll inside their own wrapper on small screens instead of breaking the layout.
- Respect `prefers-reduced-motion`; keep any animation minimal.

## Accessibility

Target WCAG 2.1 AA.

- Text contrast at least 4.5:1 in both light and dark themes.
- Visible focus styles on all interactive elements. Never `outline: none` without a replacement.
- Include a "Skip to content" link as the first focusable element.
- All images have meaningful `alt` text (or `alt=""` if decorative).
- Everything must be usable by keyboard alone.

## Print

Students will print this. Maintain an `@media print` block that hides the nav and decorative elements, uses black on white, avoids splitting table rows and headings across pages (`break-inside: avoid`), and shows link URLs where useful.

## JavaScript

- Optional enhancement only. The page must be fully usable with JS disabled.
- Vanilla ES modules or a plain script; no libraries.
- Keep it small, with no global state.

## Conventions

- 2-space indentation. Lowercase kebab-case for filenames, CSS classes, and ids.
- Class names describe what something is (`.schedule-table`), not how it looks (`.big-red`).
- Prefer editing existing files over adding new ones.
- Comments only where intent isn't obvious from the code.

## Verifying changes

There is no test suite. After a change:

1. Open `index.html` in a browser and check it at mobile (~375px) and desktop widths.
2. Check print preview.
3. Tab through the page with the keyboard.
4. Check the browser console for errors and confirm no links are broken (all nav anchors resolve).

## Don'ts

- Don't add trackers, analytics, or third-party scripts.
- Don't add a backend, forms that submit data, or user accounts.
- Don't collect or display student personal data.
- Don't add dependencies or a build tooling setup without asking first.
